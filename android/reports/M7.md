# M7 report: YouTube (site resolvers)

Branch `m7` (from `master` at `05e0b48`). Built and checked by the auditor at the owner's request.

## Decisions
- Resolver: **NewPipeExtractor v0.26.5** (GPL-3.0), YouTube only, behind a `SiteResolver` interface. yt-dlp, X, Instagram and TikTok can be added later as more resolvers. No Google Play distribution.
- **Licence consequence:** the app now links a GPL-3.0 library, so Spotter itself must be offered under GPL-3.0 to anyone who receives the APK. For personal use nothing changes. See `README.md`.

## What was built
- `resolver/` : `SiteResolver`, `OptionBuilder` (picks H.264 MP4 video + AAC M4A pairs, a one-file option and audio-only), `YoutubeResolver` (NewPipe on the app's OkHttp client), `ResolvedUrl` (the plan kept inside the download's URL field as `spotter-resolved://v1/<base64url json>`: stream links only, never cookies).
- `engine/resolved/ResolvedDownloader` : each stream is fetched as 8 MiB byte ranges, 4 at a time (the site throttles one long request), stored like HLS segments so resume never repeats a finished chunk; on 401/403/404/410 the page is looked up **once** again and the same chunks continue with fresh links (at most 3 refreshes); video and audio are merged with `MediaMuxer`; chunks are deleted only after the joined file is complete (a pause or crash while joining never forces a re-download); free-space check up front (about 2x).
- UI: `ResolveCoordinator` + `ResolveDialogHost` (looking up, quality list with exact sizes, error). Entry points: the Add-URL box, the system share sheet (YouTube app > Share > Spotter), clipboard suggestion, and the browser's "page" entry on a YouTube page.
- Build: JitPack repository restricted to `com.github.TeamNewPipe*`, core library desugaring, R8 rules for Rhino and protobuf (each rule has its failure noted in `proguard-rules.pro`).
- Remux fix found on the way: the old "+1 microsecond" timestamp fix is now applied to **audio only**; it was altering video frames that have B-frames.

## Evidence
- `./gradlew testDebugUnitTest`: **141 tests, 0 failures** (127 existing + 14 new: `OptionBuilderTest` 5, `ResolvedUrlTest` 3, `ResolvedDownloaderTest` 6). The downloader tests use a Range-capable local server and check: chunked download and join (hash equal), one-file option, audio-only, expired links refreshed exactly once, expired link without a resolver ends `NEEDS_REFRESH`, and that after pause and resume **none of the already finished chunks is requested again** (checked by path and range start).
- Emulator, debug build, real YouTube (https://www.youtube.com/watch?v=bzGU0b5XAKc, a 2:07 trailer): lookup took about 10 s and listed 1080p to 144p plus audio-only with exact sizes (24.4, 10.8, 7.4, 4.9, 3.4, 2.7 MB, audio 2.0 MB). 720p downloaded in a few seconds at about 3.2 MB/s (4 parallel chunks; one plain connection measured about 0.36 MB/s) and was saved as a 10.8 MB MP4: ffprobe h264 1280x720 + aac, duration 127.48 s, 3058 video frames and 5490 audio frames, `ffmpeg -v error -i out.mp4 -f null -` prints **nothing**, a frame at 60 s shows the right picture. A `youtu.be` short link worked the same way.
- Emulator, **signed minified release build** (2.5 MB): the same lookup and 720p download work; decode check clean; no crash.

## Not verified (stated plainly)
- Real link expiry (links last about 6 hours): covered by JVM tests only.
- The browser's YouTube page entry and the share-sheet path on a device (same code path as the Add-URL box, which was tested).
- Age-restricted, private or live videos (the resolver reports "Could not read this video").
- Android 8 and 9 (not tested by owner decision).

## Notes for later
- The same weakness M7 fixed (pause during the final join forces a re-download) exists in `HlsDownloader`: its segments are deleted while joining. Worth applying the same temporary-file pattern there.
- YouTube changes often; when it breaks, bump the NewPipeExtractor version and re-run `ResolvedDownloaderTest` and the real-link check above.
