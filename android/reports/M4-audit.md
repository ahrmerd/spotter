# M4 audit

**Verdict: PASS WITH FIXES (one blocker, two majors).** Downloading, decrypting, resuming and cleaning up HLS streams
works on a device. But the step that turns the stream into an `.mp4` fails on any realistic video, so the user ends up with a raw `.ts` file
(and, because of a naming bug, a file that cannot be found under the name shown). One blocker (E1) and two majors (E2, E3) must be fixed
before M4 is closed; they can be fixed on the `m5` branch as agreed. No redo is needed.

Audited commit: `d8743c7` (branch `m4`), merged into the audit worktree. The auditor changed no source code in this audit.

## Reproduced
- `./gradlew assembleDebug testDebugUnitTest`: build OK, **112 tests, 0 failures** (matches the report; 29 of them are HLS).
- Static checks clean: no empty `catch` in Kotlin (the only one is in the injected JavaScript), no `GlobalScope`/`runBlocking`, no keys or cookies in log statements, playlists bounded to 2 MiB, segments streamed with a 64 KiB buffer, cookies added through `CookieSource` for playlist, segment and key requests (as required by the M3 audit).

## Why the JVM evidence is not enough
The builder's HLS tests remux with the host `ffmpeg` (`FfmpegCliRemuxer`). The production remuxer on Android is `MediaMuxerRemuxer`, which was **never run** (reported NOT RUN). It is also where the M4 output format is decided, so I tested it on the emulator with streams I generated myself.

Streams (generated by me with ffmpeg, served by `tools/media_server.py` on the host, reached at `10.0.2.2`):
- `big`: 1280x720 H.264 + AAC, 16 s, noisy so key frames are large (215 KB and 81 KB), 4 segments.
- `many`: 160x120 H.264 + AAC, 900 s, **900 one-second segments**.
- `master.m3u8` pointing at both (720p at 6.5 Mbps, 160x120 at 120 kbps).

## Findings

### E1 [blocker] `MediaMuxerRemuxer` fails on any realistic video, so HLS never becomes an MP4
- Where: `engine/hls/MediaMuxerRemuxer.kt` (`ByteBuffer.allocate(64 * 1024)` used for `readSampleData`).
- Observed: the 720p stream (key frames 215 KB and 81 KB) ended as "Done · Could not remux to MP4 (IllegalArgumentException). Kept MPEG-TS." The 160x120 stream, whose frames fit in 64 KB, remuxed fine. Any 480p/720p/1080p video has frames far larger than 64 KB, so on real content the app always falls back to `.ts`. The unit tests could not see this (they remux with host ffmpeg).
- Fixed when: the sample buffer is sized from the track format (`MediaFormat.KEY_MAX_INPUT_SIZE`) with growth on a "too small" failure (and a sane ceiling), and an instrumented test remuxes a real >64 KB-frame TS fixture on the emulator and the pulled file passes `ffprobe` and `ffmpeg -v error -i out.mp4 -f null -`. The auditor will re-run my 720p stream.

### E2 [major] The `.ts` fallback is saved as `name.ts.m2ts`, but the UI shows `name.ts`
- Observed: the Downloads row says `index.ts`; the file on the phone is `Download/Spotter/index.ts.m2ts`. MediaStore appends an extension that matches the MIME type (`video/mp2t` -> `.m2ts`). The user cannot find the file under the name the app shows.
- Fixed when: the name shown equals the name on disk (for example pick a MIME/extension pair MediaStore accepts for `.ts`, or read the real display name back after saving and store that), with a device check.

### E3 [major] Peak disk usage is about four times the video size
- Where: `HlsDownloader.runJob`/`assemble`: all segments are kept as files, then copied into `assembled-video`, then remuxed into `out.mp4`, then copied into the MediaStore sink; nothing is deleted until the very end. A 1 GB stream needs about 4 GB of free space, and there is no free-space check before it starts (M5 adds one; it needs a realistic estimate).
- Fixed when: segment files are deleted as soon as they are appended, `assembled-*` is deleted after the remux, and ideally the remux writes straight to the sink or the final `.mp4` is moved rather than copied. State the new peak (for example about 2x). The M5 free-space check should use that estimate.

### E4 [minor] Remuxed audio has repeated timestamps and the tracks are not interleaved
- `ffmpeg -v error -i index.mp4 -f null -` on the 900 s result prints `Application provided invalid, non monotonically increasing dts to muxer in stream 1: 15360 >= 15360`. `MediaMuxerRemuxer` writes all samples of one extractor and then the next. Interleave by presentation time and drop or fix duplicate timestamps; fixed when the same decode check prints nothing.

### E5 [minor] Progress persistence rewrites every part row for every finished segment
- `persistLocked()` replaces the whole parts table each time a segment completes (O(N squared) row writes). At 900 segments the whole download took about 25 s on the emulator, so this is acceptable today, but a 2-hour stream with 3000+ segments will be slow. Batch it (every N segments or every second), as M1's byte downloader does.

### E6 [minor] Segment retries are too short
- `HlsHttp.MAX_ATTEMPTS = 3` with 0.25 s to 1 s backoff: a server hiccup (HTTP 429/503) or a mobile network blip longer than about 2 s fails the whole download, which the user must retry by hand (resume does work by segment). Use the same policy as M1's parts (8 attempts, backoff up to 30 s) for 5xx/429 and IO errors.

### E7 [minor] Notes
- The emulator process died four times this session (twice during this audit), each time shortly after video activity and with H.264 decoder messages from the host in its log; not attributed to the app, but note that device testing of video features is flaky on this machine.
- The report's NOT-RUN items are honest. Please update `M4.md` with the device results above or your own.

## Looks good
- The HLS engine is well structured: a parser covering master/media/key/map/byte-range, fail-closed for SAMPLE-AES, DRM and live streams, resume by segment index, work files cleaned on cancel, and no whole-segment buffering.
- Resume correctness holds on a device: after a pause at 575/900 the final video and audio are bit-identical to an uninterrupted run.
- M3 audit fixes were merged correctly, and `CookieSource` is used for the playlist, segment and key requests.
- The A1 fix from the M2 audit works on a device.
